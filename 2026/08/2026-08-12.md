## 1. Topic 통신

- 구독과 **메시지 큐**: 메모리·성능·네트워크 상황에 따라 큐 크기를 조절할 필요가 있다. 극한의 경우 SSD로 메모리 스왑하는 방법도 고려한다.
- 메시지는 종류마다 ROS가 정한 타입이 있고, **Node Graph**로 시각화할 수 있다.

```bash
# 두 개의 터미널에서 (각각 source 후)
ros2 run my_package velocity_publisher
ros2 run my_package velocity_subscriber

# 다른 터미널에서 관찰
ros2 topic list                    # /cmd_vel 이 보이는지
ros2 topic echo /cmd_vel           # 실제 메시지 내용 출력
ros2 topic hz /cmd_vel             # 20Hz로 나오는지 (주기 검증)
ros2 topic info /cmd_vel           # 발행자·구독자 수

# 디버깅용 수동 발행
ros2 topic pub /cmd_vel geometry_msgs/msg/Twist "{linear: {x: 0.2}}" --rate 10
```

대표 메시지 패키지:

| 패키지 | 대표 메시지 | 용도 |
| --- | --- | --- |
| `std_msgs` | `String`, `Float64`, `Bool` | 단순 값 |
| `geometry_msgs` | `Twist`, `Pose`, `Point` | 속도·자세·위치 |
| `sensor_msgs` | `LaserScan`, `Image`, `Imu` | 센서 데이터 |
| `nav_msgs` | `Odometry`, `Path` | 주행 정보 |

## 2. Service·Action·Parameter 통신

- **Service**: 요청-응답(request/response), 단기·즉시. 응답을 콜백에서 동기로 기다리지 않고 비동기(`call_async`)로 처리한다.
- **Action**: 장기 작업, 중간 피드백 제공.
- **Parameter**: 런타임 설정값. 다시 빌드하지 않고 값을 바꿀 수 있다.

## 3. DDS와 QoS

- **DDS**: 미들웨어로, 알아서 분산 서비스를 가능하게 한다. 기본은 Fast DDS. **QoS**로 노드의 통신 성격마다 다른 설정이 가능하다.
- 매번 세부 설정을 조합하긴 번거로워, ROS2는 용도별 **프로파일**을 제공한다.

| 프로파일 | 구성 | 용도 |
| --- | --- | --- |
| Default | Reliable, Volatile, KeepLast(10) | 일반 통신(명령 등) |
| Sensor Data | Best-Effort, Volatile, KeepLast(5) | 카메라·LiDAR 스트림 |
| Services | Reliable | 서비스 통신 |
| Parameters | Reliable | 파라미터 |

```python
from rclpy.qos import qos_profile_sensor_data

# 센서 데이터엔 전용 프로파일
self.sub = self.create_subscription(
    LaserScan, '/scan', self.on_scan, qos_profile_sensor_data)
```

## 4. TF2 좌표 변환

- **Frame**은 좌표계, **TF2(Transform Library 2)** 는 ROS의 좌표 변환 라이브러리다. 표준 계층으로 좌표계 트리를 구성한다.
- **URDF**는 로봇의 각 부분이 어떻게 연결되었는지를 기술한다.

## 5. URDF 문법 정리 (ROS2 기준)

URDF는 XML 기반으로 로봇의 **링크(부품)** 와 **조인트(관절)** 를 트리 구조로 기술한다. ROS2에서는 순수 URDF보다 **xacro**를 섞어 쓰는 게 사실상 표준이다.

**최상위 구조** — 루트 태그는 `<robot>`(name 필수), 내부에 `<link>`(노드)와 `<joint>`(엣지)를 나열한다. 부모 없는 최상위 링크(`base_link`)가 하나 있어야 하고 순환 구조는 불가하다.

```xml
<?xml version="1.0"?>
<robot name="my_robot" xmlns:xacro="http://www.ros.org/wiki/xacro">
  <link name="..."/>
  <joint name="..." type="...">...</joint>
</robot>
```

**`<link>` 구성 요소**:

| 태그 | 역할 |
| --- | --- |
| `visual` | RViz 등에서 렌더링될 형상(복잡한 mesh 가능) |
| `collision` | 충돌 계산용 형상(보통 단순화해 성능↑) |
| `inertial` | 질량·관성텐서 — Gazebo/물리 시뮬레이션에 필수, RViz만 쓸 거면 생략 가능 |

geometry 종류: `box`, `cylinder`, `sphere`, `mesh`(`.stl`/`.dae`, `package://` 경로).

**`<joint>` 타입**:

| type | 설명 |
| --- | --- |
| `fixed` | 고정(센서 마운트 등) |
| `revolute` | 회전, 각도 제한 있음(로봇 팔 관절) |
| `continuous` | 회전, 제한 없음(바퀴) |
| `prismatic` | 직선 이동, 위치 제한 있음(리니어 액추에이터) |
| `floating` | 6DOF 자유 이동(거의 안 씀) |
| `planar` | 평면상 이동 |

- `origin`: child가 parent 좌표계 기준 어디에 붙는지(xyz + rpy, 라디안).
- `axis`: revolute/continuous/prismatic에서 움직이는 축(child 링크 좌표계 기준).
- `limit`: revolute/prismatic에 필수(`lower`, `upper`, `effort`, `velocity`).

**ROS2에서 함께 쓰는 확장**:

- **xacro**: `property`(변수), `macro`(반복 구조), `include`(분리된 파일)를 지원. `xacro robot.urdf.xacro > robot.urdf`로 변환하거나 launch에서 `xacro.process_file()`로 처리. 바퀴 4개·손가락처럼 반복 구조에 필수.
- **`<ros2_control>`**: 어떤 조인트를 command/state 인터페이스로 제어할지 선언. `hardware/plugin`에 시뮬레이션용(`gazebo_ros2_control/GazeboSystem`) 또는 실기체 드라이버를 지정. 실제 제어기(`diff_drive_controller` 등)는 별도 `controllers.yaml`에서 설정해 `ros2_control_node`가 로드.
- **`<gazebo>`**: `reference`로 특정 링크에 마찰(`mu1`/`mu2`)·색상 등 Gazebo 전용 물리 속성을 부여하거나, `reference` 없이 전체 플러그인을 로딩.

**일반적 흐름**: ① `robot.urdf.xacro` 작성 → ② `ros2_control` 태그로 인터페이스 선언 → ③ `robot_state_publisher`가 `/tf`·`/robot_description` 퍼블리시 → ④ `joint_state_publisher`로 RViz 시각화 → ⑤ Gazebo에서 `<gazebo>` 플러그인이 `controllers.yaml`을 로드.

**자주 하는 실수**:

- `inertial` 값이 0이거나 비현실적이면 Gazebo에서 로봇이 날아가거나 뒤집힌다.
- `collision`에 mesh를 그대로 쓰면 물리 연산이 무겁고 불안정 → 단순 도형으로 근사 권장.
- `axis` 방향과 `origin`의 `rpy` 좌표계를 혼동하기 쉽다(axis는 child 좌표계 기준).
- xacro `${}` 수식 안에서는 단위 변환이 자동이 아니므로 항상 SI 단위(m, rad, kg)로 통일.

## 6. 결과물·기록 관리 (연사 조언)

- **김명서** — 실습·과제·프로젝트는 열심히 했지만 취업 준비 때 결과물이 흩어져 고민인 경우가 많다. 기록이 부실해지는 이유는 ① 왜 발생했고 왜 그 해결법을 택했는지 **사고 과정**을 안 적어서, ② 결과를 잘 낼수록 과정이 기억나지 않아서다. 초반부일수록 기록에서 빠지기 쉽다.
  - 실패한 경험도 가설-검증 구조로 적으면 자산이 된다(예: 가설을 세우고 ANOVA로 검증 → "상관없음"이라는 결과도 기록).
  - 경험 정리용 페이지는 **STARR 형식**으로 통일. 정말 귀찮을 땐 클로바노트로 말하듯 회고하고 텍스트 변환 후 AI에게 정리를 맡긴다.
  - 결국 문제없는 프로젝트는 없고, 끝까지 포기하지 않고 해결하려는 자세가 중요하다.
- **백하은 (TIL 작성법)** — 파일·디렉토리도 정해진 법칙대로 저장. TIL은 개념보다 **사용한 맥락**을 적고, 바쁠 땐 간단히, 주말에 여유 있을 때 다시 본다.
